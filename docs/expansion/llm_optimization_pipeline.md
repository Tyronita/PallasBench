# LLM-Driven Kernel Optimization Training Data Pipeline

## Goal

Generate optimized versions of each PallasBench kernel using LLMs, building a dataset of `(unoptimized_kernel, optimized_kernel, speedup)` triples suitable for SFT (supervised fine-tuning) and RL (reinforcement learning with reward = speedup) training of code-generation models.

---

## Pipeline Stages

### a. Prompt Engineering

Each prompt must communicate:

1. **The unoptimized Pallas kernel source** — the TPU-oriented version from PallasBench.
2. **The JAX reference implementation** — so the LLM can verify semantic intent.
3. **Hardware context** — GPU model (A100 80GB), SM count (108), warp size (32), shared memory (164 KB/SM), L2 cache (40 MB), HBM bandwidth (2039 GB/s).
4. **Optimization targets**:
   - Block size tuning for SM occupancy
   - Tiling strategy for GPU memory hierarchy (HBM → L2 → registers)
   - Memory coalescing and aligned access
   - Loop unrolling and pipelining
   - Use of `jnp` operations with minimal reshapes
   - Avoidance of the Triton 1M-element ceiling (clamp blocks at 65,536 elements max)
5. **Output constraint**: Must be a valid Pallas `pl.pallas_call` kernel that compiles on A100.

Prompt template (Level 1 — single operator):

```
You are optimizing a Pallas kernel for NVIDIA A100 GPU (CC 8.0, 108 SMs, 2039 GB/s HBM).
Below is the reference implementation and the current unoptimized kernel.

## Reference (JAX)
```python
{reference_source}
```

## Current Kernel (Pallas, unoptimized)
```python
{kernel_source}
```

## Hardware Context
- GPU: NVIDIA A100 80GB PCIe
- SMs: 108, Warp size: 32
- Shared memory: 164 KB per SM
- L2 cache: 40 MB
- HBM bandwidth: 2039 GB/s peak
- Triton element limit: 1,048,576 per block dimension
- JAX + Pallas with Triton backend

## Optimization Guidelines
- Choose {block_size} to maximize SM occupancy ({num_blocks} blocks needed for full occupancy)
- Ensure blocks respect the Triton 1M element ceiling
- Use contiguous memory access patterns within each block
- Minimize redundant recomputation
- Keep the function signature identical: `def kernel_fn(x_ref, o_ref):`

## Output
Return ONLY the optimized Pallas kernel body inside a code block. Do NOT include the `pallas_call` wrapper — just the kernel function.
```

**Level 2 (fused patterns)** adds a section describing which operators should be fused and why:

```
## Fusion Goal
- Fuse {op1} and {op2} into a single Pallas kernel to reduce global memory traffic
- The fused kernel should read inputs once, compute both operations, and write the result once
```

**Level 3 (architecture components)** adds tiling strategy for multi-dimensional blocks:

```
## Tiling Strategy
- Input: {input_shape} with reduction dimension {K}
- Use 2D block tiling: BLOCK_M × BLOCK_N × BLOCK_K
- Pipeline loads along the K dimension
- Accumulate in float32, write in {output_dtype}
```

### b. Generation

Candidate kernels are generated by querying LLM APIs. The pipeline supports multiple providers:

| Provider | Models | Notes |
|----------|--------|-------|
| OpenAI | GPT-4o, o1, o3-mini | Strong general coding; high cost |
| Anthropic | Claude Opus 4, Sonnet 4 | Best for Pallas DSL knowledge |
| Open-source | Llama 4, DeepSeek-Coder-V2, Qwen3-Coder | Run locally via vLLM; lower cost, lower quality |
| Perplexity | Sonar Huge | Alternative API |

Generation protocol:

```python
def generate_candidates(
    kernel_name: str,
    kernel_source: str,
    reference_source: str,
    model: str,
    n: int = 5,
    temperature: float = 0.8,
) -> list[dict]:
    """Generate n candidate kernels using the specified LLM.

    Returns list of dicts with keys:
      - candidate_id: str
      - kernel_source: str  (the optimized Pallas kernel body)
      - model: str
      - temperature: float
      - prompt: str          (full prompt sent)
      - raw_response: str    (full response for audit)
    """
```

Key parameters:
- **n candidates per kernel**: start with 5, scale to 20+
- **temperature**: 0.8 for diverse exploration, 0.2 for exploitation
- **best-of-n**: generate N, keep top K by estimated quality

### c. Evaluation

Each candidate kernel is evaluated using the robust evaluation framework defined in `pallasbench/robust_eval/evaluator.py`:

1. **Compilation check**: Does the kernel compile via `jax.jit` + `pallas_call`?
2. **Correctness**: Does output match JAX reference via `jnp.allclose(atol=1e-5, rtol=1e-5)`?
3. **Robustness filters** (5 checks from Section 5.2 of robust evaluation report):
   - Output Range Filter
   - Output Std Filter
   - Axes Variation Filter
   - Input Impact Filter
   - Source Analysis Filter
4. **Performance measurement**:
   - JIT compilation time (wall clock, minutes-scale)
   - Kernel execution time (warm cache, microseconds-scale)
   - Throughput (GB/s, GFLOP/s)
   - Bandwidth utilization (% of 2039 GB/s peak)

Full evaluation output per candidate includes the complete `KernelEvalResult` dataclass.

### d. Selection — Tournament

After evaluating all candidates for a given kernel, select the best using tournament ranking:

```python
def tournament_select(
    candidates: list[EvalResult],
    k: int = 3,
) -> list[EvalResult]:
    """Return top-k candidates by (correctness, speedup) pareto front.

    Ranking:
    1. Correctness (binary: pass all robustness filters)
    2. Speedup (float: baseline_time / kernel_time)
    3. Compilation time (lower is better — proxy for simplicity)
    """
```

Ties are broken by bandwidth utilization (higher = better-optimized for GPU).

### e. Dataset Construction

**SFT format** (supervised fine-tuning — `instruction` + `output`):

```jsonl
{"instruction": "Optimize this Pallas kernel for A100 GPU:\n\n```python\n...original kernel...\n```", "output": "```python\n...optimized kernel...\n```"}
```

**RL format** (reward model training — `prompt` + `chosen` + `rejected`):

```jsonl
{"prompt": "Optimize this Pallas kernel for A100 GPU:\n\n```python\n...original kernel...\n```", "chosen": "```python\n...best kernel (speedup=X.1x)...\n```", "rejected": "```python\n...worst kernel that passes correctness (speedup=0.8x)...\n```"}
```

**KernelBook format** (unified cross-benchmark JSONL):

```jsonl
{
  "kernel_name": "relu",
  "level": 1,
  "category": "activation",
  "source_original": "def relu_kernel(x_ref, o_ref):\n    o_ref[...] = jnp.maximum(x_ref[...], 0.0)\n",
  "candidates": [
    {
      "candidate_id": "relu--gpt4o--0",
      "model": "gpt-4o",
      "temperature": 0.8,
      "source_optimized": "...",
      "speedup": 1.25,
      "correctness_passed": true,
      "robustness_passed": true,
      "jit_compile_time_seconds": 412.3,
      "kernel_exec_time_seconds": 0.00015,
      "bandwidth_utilization_pct": 82.6,
      "gpu_memory_used_bytes": 65536
    }
  ],
  "result_best": {
    "speedup": 1.25,
    "candidate_id": "relu--gpt4o--0"
  }
}
```

## Template Prompts

### L1 — Single Operator (ReLU)

```
Optimize this Pallas kernel for NVIDIA A100 GPU.

### Reference (JAX)
```python
def relu_reference(x):
    return jnp.maximum(x, 0.0)
```

### Current Kernel (Pallas, unoptimized)
```python
def relu_kernel(x_ref, o_ref):
    o_ref[...] = jnp.maximum(x_ref[...], 0.0)
```

### Hardware
- A100 80GB PCIe, 108 SMs, 2039 GB/s HBM
- Block dimension limit: 1,048,576 elements
- Input shape: (4096,), block_size = min(1024, n) → clamped to 64

### Optimization Targets
1. Increase from 64 → 4096 elements per block (respects 1M limit for 1D)
2. Use float32 accumulation
3. Minimize grid size for lower scheduling overhead

Return ONLY the optimized kernel function in a code block.
```

### L2 — Fused Pattern (MatMul + GELU)

```
Optimize this fused Pallas kernel for NVIDIA A100 GPU.

### Reference (JAX)
```python
def fused_matmul_gelu_reference(x, w, b):
    return jnp.dot(x, w) + b, jax.nn.gelu(jnp.dot(x, w) + b)
```

### Current Kernel (Pallas, unoptimized)
```python
def fused_matmul_gelu_kernel(x_ref, w_ref, b_ref, out_ref):
    x = x_ref[...]
    w = w_ref[...]
    b = b_ref[...]
    out_ref[...] = jnp.dot(x, w) + b
```

### Hardware
- A100 80GB PCIe, 108 SMs, 2039 GB/s HBM
- Block limit: 1M elements per dimension
- Input: (M, K) @ (K, N) → output: (M, N)

### Optimization Targets
1. 2D block tiling: BLOCK_M × BLOCK_N × BLOCK_K
2. Pipeline matmul along K dimension
3. Fuse GELU into the output write to avoid separate kernel launch
4. Use float32 accumulator for matmul

Return ONLY the optimized kernel function in a code block.
```

### L3 — Architecture Component (Flash Attention)

```
Optimize this flash attention Pallas kernel for NVIDIA A100 GPU.

### Reference (JAX)
```python
def attention_reference(q, k, v):
    scores = jnp.dot(q, k.T) / jnp.sqrt(q.shape[-1])
    weights = jax.nn.softmax(scores)
    return jnp.dot(weights, v)
```

### Current Kernel (Pallas, unoptimized)
```python
def attention_kernel(q_ref, k_ref, v_ref, o_ref):
    q = q_ref[...]
    k = k_ref[...]
    v = v_ref[...]
    attn = jnp.dot(q, jnp.transpose(k)) / jnp.sqrt(q.shape[-1])
    attn = jax.nn.softmax(attn)
    o_ref[...] = jnp.dot(attn, v)
```

### Hardware
- A100 80GB PCIe, 108 SMs, 2039 GB/s HBM
- Shared memory: 164 KB per SM
- Block limit: 1M elements per dimension

### Optimization Targets
1. Tiled online softmax (no materialization of full attention matrix)
2. Block-sparse tiling in QK and PV dimensions
3. Use shared memory for K/V blocks
4. Pipeline matmul and softmax within each tile

Return ONLY the optimized kernel function in a code block.
```

## Expected Challenges

### 1. JIT Compilation Bottleneck (~400s per eval)

Each candidate kernel requires a full JIT compilation, dominated by `ptxas` assembly (400+ seconds). For 45 kernels × 5 candidates × 3 models = 675 evaluations, that's 675 × 400s = **270,000s = 75 hours** of GPU wall time.

**Mitigations**:
- Use warm-cache evaluation after initial compile (subsequent runs ≈ 0.0002s)
- Run evaluations in parallel across multiple A100 GPUs
- Cache compiled kernels by StableHLO hash to avoid recompiling identical candidates
- Pre-filter candidates with static analysis (source analysis filter) before GPU compilation

### 2. LLM API Costs

| Provider | Model | Cost/1M tokens | 1M output tokens | Est. per 1K candidates |
|----------|-------|----------------|------------------|----------------------|
| OpenAI | GPT-4o | $2.50 / $10.00 | 1K prompts ≈ $15-30 |
| Anthropic | Claude Opus 4 | $15.00 / $75.00 | 1K prompts ≈ $80-150 |
| Open-source | DeepSeek-Coder-V2 | Free (self-hosted) | GPU compute cost only |

**Mitigation**: Use open-source models for exploration, frontier models for final dataset. Prompt caching (Anthropic) reduces costs for repeated context.

### 3. Hallucinated APIs

MultiKernelBench found 22.4% of LLM-generated Pallas kernels contain hallucinated `pallas_call` keyword arguments.

**Mitigation**:
- Include the exact function signature and import line in every prompt
- Add source analysis filter that rejects kernels with unknown keyword arguments
- Static AST check: parse the generated kernel and verify it uses only valid `pl.*` primitives

### 4. Surface-Level Optimizations

LLMs may make cosmetic changes (renaming variables, adding comments) without changing performance. The speedup signal will be near 1.0x for these.

**Mitigation**:
- Only include candidates with speedup > 1.05 in the training dataset
- The RL reward model must learn to distinguish real optimizations from surface changes
- Report "effective optimization rate" — fraction of candidates with speedup > 1.1

## Integration with ShinkaEvolve

The LLM-generated candidates form the initial population for ShinkaEvolve's evolutionary optimization:

1. **Seed population**: LLM-generated kernels (from this pipeline)
2. **Mutation**: "Tune block sizes by ±50%" or "Swap tiling order" — LLM-guided mutation
3. **Crossover**: Combine block spec from candidate A with reduction logic from candidate B
4. **Selection**: Tournament selection using correctness + speedup as fitness
5. **Evolutionary trace**: Full lineage of each improvement captured for RL training data

This integration produces a richer training signal than static generation alone — the evolutionary trace shows *how* kernel improvement happens step by step, which is valuable for training models to reason about optimization.
